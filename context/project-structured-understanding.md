> **文档状态**：候选项目上下文，供项目成员和表达 Agent 理解使用；不是项目事实源、正式治理制度、技术验收文件或发布授权文件。
> **整理日期**：2026-10-28
> **理解对象**：大连理工结构力学计算异构并行项目及其对外表达资产
> **理解主体**：参与项目协作、事实整理和对外表达准备的成员与 Agent

## 一、理解主体与理解对象

本文档帮助项目成员和表达 Agent 理解项目整体实践：项目为什么存在，哪些对象参与其中，谁在什么边界内承担责任，什么材料可以支撑什么主张，以及如何把专业事实组织为面向特定受众的表达作品。

项目的正式名称为**大连理工结构力学计算异构并行项目**。本文中的“项目”指由合作目标、范围、阶段责任、专业工作和外部协作共同构成的实践对象；“项目小组”指围绕该项目形成的成员、专业能力、任务责任和协作关系。项目和项目小组相关，但不互相等同：项目存在不证明项目小组已经有效形成，成员参与也不自动说明其拥有全部项目责任或授权。

需要分开理解以下载体：

| 对象 | 主要职责 | 与本项目的关系 | 不应据此推出 |
| --- | --- | --- | --- |
| **大工项目** | 规定合作目标、范围、问题语境、阶段判断和交付关系 | 本文的主要理解对象 | 项目已经完成或技术路线已经确定 |
| **项目小组** | 在实际授权和资源条件下组织成员、专业能力和任务执行 | 项目的执行协作关系；具体成员和授权需回到记录核对 | 项目小组天然拥有合同、验收或公开发布权 |
| **`houzai` 项目源仓库** | 保存专业事实、研发代码、任务、会议、实验和长期项目资产 | 项目专业事实的主要来源 | 源仓库中任何文件都自动适合 public 发布 |
| **大工项目对外表达资产仓库** | 保存脱敏上下文、表达任务、作品、来源登记、评审和确认记录 | 为成员和 Agent 提供 public 表达上下文 | 它已经成为项目专业事实的唯一数据库 |
| **基础设施 submodule** | 提供固定版本的通用工具、模板、技能、Harness 和检查协议 | 为表达资产仓库提供通用能力；当前能力以 Manifest 为准 | 其中的能力目录或计划自动适用于本项目 |
| **SuanhaiOS 相关能力** | 为成员提供任务环境、协作支持和团队级能力入口 | 可以辅助项目执行和上下文访问 | 它是本项目技术事实、技术验收或发布授权的主位 |

本文是项目资料的工作性理解。项目事实、任务责任、技术结论和发布授权仍须回到来源和真人确认记录核对。

## 二、背景与理解目标

### 2.1 项目为什么存在

项目面向既有结构力学有限元 CPU/MPI 求解体系，处理真实结构计算中的模型、网格、约束、分区、线性求解和结果恢复问题。现有流程已经能够承载部分计算，但复杂约束和自由度结构可能造成分区负载不均，区域分解和迭代法可能出现不收敛或零主元，TensorFem 的数据准备、后端交接和 GPU 通信也可能限制异构执行收益。

这些问题同时涉及数学结构、软件实现、计算环境和合作方使用条件，不能靠某一次算法测试或单个加速数字完成判断。项目需要把工程预备、性能专项和架构设计放到可说明的算例、版本、环境、正确性、残差、计时和资源条件下共同观察。

### 2.2 项目的现实价值

当前资料支持从四个角度理解项目价值，但不表示每个项目阶段都能同时实现全部价值：

| 价值维度 | 项目可能提供的价值 | 判断限制 |
| --- | --- | --- |
| 工程价值 | 发现真实软件流程中的分区、求解、数据和资源问题，形成可验证的改进路径 | 单次测试不能代表所有模型或生产环境 |
| 合作决策价值 | 为接口衔接、架构重构、资源采购和后续范围提供证据 | 方案仍需通过正确性、适用性和投入评估 |
| 长期能力价值 | 可能沉淀可复用的数学理解、软件模块、测试方法和计算经验 | 产出只有经过审查、维护和责任接续才可能成为长期能力 |
| 成员实践价值 | 让成员在真实问题中学习建模、验证、工程协作和责任判断 | 参加任务不自动等于能力已经形成或获得正式授权 |

### 2.3 结构化理解希望帮助什么

本文希望帮助成员和 Agent：

1. 先理解项目目标、场景、协作关系和约束，再阅读局部任务；
2. 把工程事实、技术判断、证据、候选方案、计划和授权分开记录；
3. 识别当前工作对项目整体交付、风险、资源和下一步决策的影响；
4. 从专业事实源中形成可追溯、适用边界清楚的对外表达。

本文不建立项目管理制度、人员考核制度、合同模板、技术验收标准、统一会议制度或自动授权机制。

## 三、一级实践对象

一级实践对象描述项目实践本身：项目规定整体语境，场景描述一次实践条件，协作结构组织责任关系，任务承载具体工作。它们与二级支撑对象不同，不能用报告、主线或状态替代。

### 3.1 项目

项目规定合作目标、工作范围、外部关系、阶段判断和交付语境，并把多个场景、任务和长期问题域放在同一个责任背景下。项目不是某个仓库、报告、会议或技术路线；签约、启动或形成会议材料，也不等于技术路线已经确定、项目小组已经有效成立或交付已经完成。

当前项目的工作性定义是：围绕既有结构力学 CPU/MPI 求解体系，针对工程环境、性能瓶颈和异构并行架构形成可复核阶段证据，并据此判断后续接口、集成、资源和范围。这个定义来自项目源材料的归纳，不是新增合同承诺。

### 3.2 场景

场景描述一次实践实际发生的条件。一个场景至少需要能够回答以下问题：

| 字段 | 说明 |
| --- | --- |
| 目标 | 本次实践要判断或完成什么 |
| 算例与输入 | 使用什么模型、网格、约束、材料和载荷 |
| 环境与版本 | 使用什么源码、依赖、编译器、MPI、硬件和配置 |
| 参与角色 | 谁执行、谁提供专业判断、谁复核、谁接收结果 |
| 主线关联 | 与工程预备、性能专项、架构设计中的哪些方向相关 |
| 正确性与计量口径 | 参考结果、残差、容差、计时范围、内存和通信指标 |
| 资源与限制 | 计算资源、权限、数据、时间和适用边界 |
| 证据与结果状态 | 形成什么记录，属于已确认、有证据未验收、计划还是待核对 |
| 受众与用途 | 内部研究、双方讨论、阶段汇报、验收说明或其他用途 |

从源材料可以确认项目已经发生过以下**场景实例**，但它们尚未构成一份正式、封闭的场景目录：

- 工程环境、构建和运行基线场景；
- 网格分区与任务划分验证场景；
- 区域分解、BDDC、直接法和迭代法求解验证场景；
- TensorFem CPU/GPU、多进程和分阶段对照场景；
- 架构接口、数据边界和异构接入讨论场景；
- 内部技术评审和外部阶段汇报场景。

这些场景可以共享一个算例或一组证据，也可以因目标、版本、受众和资源不同而分别记录。场景不是工作主线，也不是任务状态。

### 3.3 协作结构

协作结构组织项目参与成员、角色、专业能力、责任、依赖、协作接口和授权边界。当前的工作性理解是：项目小组与项目具有一一对应的组织关系，但具体成员名单、角色归属、投入承诺和正式授权仍需回到受控记录核对。

角色级责任可以这样理解：

| 角色 | 主要责任 | 边界 |
| --- | --- | --- |
| 项目经理 | 组织目标、任务、依赖、状态、风险、审查、外部协作和交付影响判断 | 不替代技术负责人做专业结论，不自行改变合同和重大资源承诺 |
| 技术负责人 | 判断技术方案、正确性、适用性、证据缺口和验证路径 | 不因承担技术判断而自动拥有合同签署或发布授权 |
| 任务负责人/执行成员 | 按任务契约开展工作，提交结果、证据、限制和未解决问题 | 完成任务不等于产出已通过审查 |
| 主线责任人 | 维护通过审查后进入主线的长期项目资产和边界 | 不把未审查的初始产出直接当作长期事实源 |
| 项目审查责任 | 联合适当技术责任人检查目标、证据、事实状态、适用边界和披露条件 | 项目审查不替代客户验收或专业领域的最终技术判断 |
| 科研小组/专业团队 | 在已有研究和人才培养关系下提供匹配的数学、算法、软件或应用能力 | 不应被当作可以随时抽调的无边界人力池；投入需要真实承诺和优先级协调 |
| 外部合作方/客户 | 提供需求、算例、使用场景、接口信息、反馈和约定验收输入 | 提供反馈不等于自动确认所有技术结论或发布范围 |
| Agent/工具 | 检索、整理、分析、生成草稿、检查结构和执行已授权的机械操作 | 不能自动成为真人责任主体、验收人或发布授权人 |

跨科研小组协作时，关键不是名单上出现了多少人，而是要分别判断：专业能力是否匹配、成员是否实际可用、投入是否被明确承诺、执行中是否形成了预期结果。名单、口头同意、会议发言或代码提交都不能单独证明项目获得了可靠投入。

### 3.4 任务

任务承载项目中的一项具体工作，通常由 Issue 或任务契约描述。一个可执行任务至少应明确：

| 要素 | 要回答的问题 |
| --- | --- |
| 目标 | 要解决什么问题，服务哪个项目判断或场景 |
| 输入 | 需要哪些算例、代码、数据、环境、来源和权限 |
| 执行者 | 谁负责执行，谁提供协作，Agent 能够执行哪些辅助动作 |
| 依赖 | 依赖哪些主线、接口、资源、前置任务或外部反馈 |
| 完成条件 | 形成什么结果、证据、限制和可复核记录 |
| 审查与收口 | 谁检查，如何处理通过、退回、保留为证据或转为长期资产 |

任务可以关联一条或多条工作主线，也可以在一个场景中与其他任务并行。任务不等于项目、产出或证据；任务已创建或已完成，不自动说明产出已提交、已审查、已晋级或可公开。

## 四、二级支撑对象

二级对象支撑一级实践对象被分类、执行、记录、追溯、评审和表达。它们不是和项目、场景、协作结构、任务完全同层的实践主体。

| 对象 | 它是什么 | 主要作用和关系 | 它不是什么 | 当前采用状态 |
| --- | --- | --- | --- | --- |
| **工作主线** | 按长期问题域组织工作的分类 | 组织任务、产出和长期资产；当前为工程预备、性能专项、架构设计 | 不是项目阶段或固定先后流程 | 已在源仓库采用 |
| **产出** | 任务形成的报告、代码变更、实验记录、图表或演示材料 | 接受审查，可能进入主线长期资产或表达作品 | 不是证据本身，也不是天然正确的结论 | 已在源仓库采用 |
| **证据** | 支撑事实或判断的测试、日志、源码核对、数据和记录 | 限定产出主张的适用条件和可信程度 | 不是结论，也不因数量多自动构成验收 | 已采用为项目判断要求 |
| **来源** | 提供事实、判断或过程依据的原始或派生材料 | 让摘要和作品可以追溯到版本、路径、日期和状态 | 不是所有来源都可公开 | 已在资产仓库登记 |
| **评审** | 对产出事实、技术质量、适用边界、归属和用途的检查 | 判断产出是否退回、保留、晋级或进入某次表达 | 不是 CI 通过、文件存在或会议讨论的同义词 | 源仓库已有晋级流程；具体记录逐项确认 |
| **状态** | 描述不同对象所处位置的独立维度 | 分开记录项目阶段、任务执行、产出生命周期、事实状态和授权状态 | 不是覆盖所有对象的总分或成熟度等级 | 已采用为上下文模型 |
| **责任与授权** | 说明谁对执行、技术判断、审查、验收和特定受众发布负责或有权限 | 约束协作、升级和发布 | 不是由文件作者、Agent 或 public 仓库自动产生的权力 | 角色边界为候选模型，主体待确认 |
| **对外表达作品** | 面向特定受众和用途组织的报告、页面、图表或演示 | 从已核验且获准使用的信息中编排，关联来源、评审和授权 | 不是专业事实源或发布授权本身 | 已登记为资产类型，具体作品逐项确认 |

工作主线、产出、证据、来源和评审共同支撑任务及项目判断；状态描述它们各自的生命周期；责任与授权决定谁可以执行、确认和发布；对外作品只负责面向受众的组织表达。

## 五、项目价值、承接和资源关系

### 5.1 项目承接与成立性

项目是否值得承接，不能只看技术兴趣或单个任务是否可行，还要结合合作价值、目标和范围、技术可行性、资源条件、已有承诺、机会成本和外部责任。项目开始或已有外部沟通，不等于必要的执行组织和资源已经成立。

项目成立性至少需要观察：目标和范围是否清楚，必要角色是否存在，能力投入是否真实可用，关键技术和数据条件是否可获得，责任和升级路径是否明确。当前资产仓库没有足够依据认定这些条件已经全部满足，具体项目成立判断需由相应责任主体确认。

### 5.2 资源投入的四层判断

项目资源不能只用人员名单表示，至少要区分：

1. 专业能力是否匹配任务；
2. 成员在已有研究、交付和培养责任下是否实际可用；
3. 投入时间、权限、算力和协作是否得到明确承诺；
4. 执行中是否真正形成了预期结果和可复核证据。

资源冲突可以先在任务内部协调；影响跨主线或跨科研小组时，需要项目经理、相关负责人和成员共同调整；涉及重大资源不足、外部承诺或合同变化时，应升级到具备相应组织授权的主体。项目经理负责把影响和选项说清楚，不自动拥有所有资源裁决权。

### 5.3 技术失败、资源不足和承诺变化

当算例不收敛、零主元、分区收益不稳定、GPU 资源不足或接口条件发生变化时，应记录事实、影响、证据缺口和可选行动。可选行动包括补充验证、引入专业支持、调整范围、调整期限、改变资源方案或暂缓高风险交付。技术负责人判断技术路径和证据要求，项目经理组织项目影响判断和协作升级，具备相应授权的主体决定合同、重大资源和正式承诺变化。

不能用“已经有报告”“已经开会”或“成员已经开始工作”替代对风险影响和下一步承接的判断。

### 5.4 项目成果转化为长期能力的条件

项目中的代码、方法、测试记录、知识和成员经验，只有在对象职责、事实质量、权益边界、维护责任和后续资源都得到确认后，才可能转化为长期软件能力、知识资产或成员能力。项目经理负责让可能的转化机会和遗留问题可见；技术负责人、主线责任人、科研小组和组织授权主体分别判断技术质量、维护价值、研究价值、人员发展和资源承接。

因此，以下关系不能自动成立：一次项目交付不自动形成稳定软件能力；一次任务参与不自动证明成员能力已经形成；出现工程问题不自动构成值得持续研究的科学问题；产生代码不自动意味着可以进入其他产品或知识体系。是否转化、由谁维护以及是否继续投入，应在项目结束或阶段评审时分别确认。

## 六、项目生命周期与责任接续

项目小组和项目交付不必同步结束，至少应分别判断以下维度：

| 维度 | 需要回答的问题 |
| --- | --- |
| 成立性 | 目标、范围、角色、能力投入和升级路径是否足以开始可靠执行 |
| 健康性 | 重要变化、技术风险、资源冲突和外部需求是否能被及时看见并承接 |
| 交付可信性 | 当前结果和证据在什么条件下支撑约定目标和预期用途 |
| 调整能力 | 需求、算例、资源或技术路线变化时，能否重新判断范围和责任 |
| 退出与责任接续 | 客户交付、遗留问题、维护支持、资料、权限和成员释放由谁接续 |

项目阶段性完成不自动说明维护、支持、权益、知识和长期软件责任已经安排。项目结束时，应分别处理客户验收、遗留风险、后续支持、资料归档、成员资源释放和潜在长期能力去向。

## 七、CAX 项目的验证、确认与交付

结构力学计算项目需要把数学模型、数值方法、软件实现、运行结果和工程使用边界联系起来。以下四种判断不能互相替代：

| 判断 | 主要问题 | 典型依据 |
| --- | --- | --- |
| **验证 Verification** | 实现是否符合已明确的模型、接口、公式、规格或完成判据 | 代码核对、单元测试、解析解、离散结果和接口检查 |
| **确认 Validation** | 在规定真实场景和使用边界内，结果是否足以支撑预期用途 | 代表性工程算例、参考结果、使用条件和适用范围 |
| **客户验收** | 合作方是否按约定目标、材料和条件接收阶段或最终交付 | 双方确认记录、验收条目、约定版本和范围 |
| **项目责任收口** | 交付、遗留问题、后续支持、权限、资料和责任是否得到接续 | 项目收尾记录、责任移交、支持安排和授权记录 |

程序运行成功、软件检查通过、数值解收敛或单个算例与基线一致，都不能单独证明模型已经适用于真实工程，也不能单独构成客户验收或项目责任收口。

## 八、汇报材料作为共同判断工作台

双周报告、会议纪要和演示材料的作用，是把与当前判断有关的目标、事实、证据、解释、限制、风险和协作请求组织成共同可观察、可质询和可行动的内容。它们不应变成按成员罗列工作量的清单，也不应通过页面完整掩盖证据缺口。

同一底层事实可以服务内部技术评审、双方阶段汇报和项目复盘，但需要根据受众和用途重新组织。内部材料不能未经审查和授权直接转为公开表达；预测、观察、建议、正式结论和合同承诺必须分别标记。

## 十、状态维度和不可自动推导关系

| 状态维度 | 记录什么 | 不能自动推出 |
| --- | --- | --- |
| 项目整体阶段 | 准备、阶段验证、工程可行性判断、集成或收尾等工作性判断 | 某项技术结果已经验收 |
| 工作主线状态 | 每条主线当前任务、证据、依赖和限制 | 三条主线已经完成或可以互相替代 |
| 任务执行状态 | 已创建、执行中、已完成、暂停或取消 | 产出已审查、已晋级或可公开 |
| 产出生命周期 | 未提交、已提交、审查中、已通过、退回、归档或已晋级 | 技术事实一定正确或内容获得授权 |
| 技术事实和证据状态 | 已确认、有证据但未验收、草稿/计划、待核对 | 项目完成或客户接受 |
| 对外披露授权状态 | 待确认、限定授权、已授权、过期或撤回 | 源资料全部可公开或技术结论已验收 |

有报告、有测试、有会议纪要、有代码提交、文件进入仓库、CI 检查通过或作品已经生成，都只能说明一个过程事实，不能自动推出项目完成、技术验收或公开授权。

## 十一、依据、不确定性与实践接口

### 11.1 当前认识的依据

项目身份、三条主线和产出晋级流程来自 `houzai` 项目与主线索引；截至 2026-10-23 的阶段判断来自对外双周报、会议整理稿及三份方向附件。具体来源、版本、路径、事实状态和授权状态见 [`sources.md`](./sources.md)。

10 月 23 日材料仍有“会后整理稿、待参会各方核对”或“阶段材料、未验收”的限制。网格分区、BDDC 和 TensorFem 的阶段结果只能在对应算例、环境、配置、正确性和计时口径下使用。

### 11.2 当前候选机制和待确认事项

以下内容是支持项目实践的候选机制，不是已经启用的统一制度：

- 由项目经理组织周级状态、影响、风险和下一步判断；
- 由项目经理联合技术责任人开展产出事实审查；
- 重大技术风险、资源冲突和承诺变化按影响和权限及时升级；
- 通过主线长期资产、报告和评审记录分别维护事实、表达和授权。

仍待确认的内容包括：实际成员名单、角色主体、正式授权链、场景目录、任务与主线映射、技术审查人、客户验收人、发布授权人以及项目结束后的支持与维护责任。

### 11.3 实践接口

后续可用具体任务检验本模型：观察任务是否明确了输入、依赖、完成条件和证据要求；成员是否有真实能力和时间投入；项目经理是否能够形成整体影响判断；技术负责人是否能够指出证据缺口；审查和授权是否真正改变了后续行动。

模型本身不启用新的岗位、会议、评分或阶段门禁。只有在真实项目中形成稳定且经责任主体确认的运行关系后，才考虑是否需要新增指南、模板或工作流。
