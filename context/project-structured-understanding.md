# 大连理工项目结构化理解

> **文档状态**：候选项目上下文，供项目成员和表达任务理解使用；不是项目正式裁决
> **整理日期**：2026-10-28
> **依据**：项目源仓库中的项目上下文索引、工作主线索引、产出审查与晋级流程，以及本资产仓库已登记的来源

## 1. 这份文档解决什么问题

已有的项目概览、状态快照和工作主线分别回答“项目是什么”“目前有什么进展”“工作如何分类”。本文件把这些信息放到同一个模型中，说明项目实践由哪些对象构成、它们怎样关联，以及一次对外表达任务应从哪里取得事实。

它是导航和理解模型，不是新的事实源。项目的最新状态、技术结论、任务责任和披露授权，仍须回到对应来源核验。

## 2. 项目定义

**大连理工结构力学计算异构并行项目**是一项外部合作项目，围绕既有结构有限元 CPU/MPI 求解体系，推进工程条件准备、性能问题验证和异构并行架构研究，为后续接口衔接、工程集成和范围判断积累可复核的阶段证据。

项目关注的不是孤立的一次算法测试或加速数字，而是相关工作能否在可说明的算例、环境、版本、正确性与计量口径下相互衔接。当前这段定义是对已有项目材料的归纳；它不表示项目已经完成统一验证或工程验收。

## 3. 核心实践对象

下表用于解释本项目中的实践关系。项目资料已明确的部分按现有结构描述；尚未在项目来源中正式登记的部分保留为理解框架，不当作已存在的项目制度。

| 对象 | 在本项目中的含义 | 关系与边界 |
| --- | --- | --- |
| **项目** | 设定合作目标、工作范围和阶段性判断边界 | 包含多条工作主线和反复发生的实践场景；不等同于某个代码仓库或一份汇报材料 |
| **协作结构** | 承载项目参与者、角色和协作责任的组织关系；项目小组与项目一一对应是当前团队的组织约定 | 具体成员、角色分配、审批权和责任链必须由有效项目记录确认；不能从代码提交或历史文档自行推定 |
| **场景** | 一次实践发生时的具体条件，例如环境准备、性能验证、架构比较或对外沟通 | 同一项目会涉及多个场景，同类场景也可能在不同项目中重复出现；本项目尚未形成完整、正式的场景清单 |
| **任务** | 为解决一个具体问题而开展的工作，通常需要明确目标、输入、执行安排和结果要求 | 任务可能关联一条或多条工作主线，并在具体场景中执行；执行状态以对应 Issue 或任务记录为准 |

项目里的 Agent 或工具可以参与信息整理、分析或执行工作，但这不自动使其成为本项目已登记的成员、责任主体或验收人。人员安排与责任归属仍须以正式记录为准。

## 4. 项目工作主线与场景

本项目当前以三条稳定工作主线组织长期方向：**工程预备、性能专项、架构设计**。它们是项目内的工作分类，不是三个连续阶段，也不是场景的同义词。

- **工程预备**：关注访问、源码、构建、依赖、配置和计算资源等可复现条件。
- **性能专项**：关注性能基线、热点、并行测试、预条件子、求解器和数据路径等验证问题。
- **架构设计**：关注现有系统边界、多后端、MPI、异构并行、接口衔接与迁移条件。

场景描述某项实践实际发生的条件。比如，一次性能对照可能依赖已经准备好的工程环境，也可能为架构判断提供证据；它可以同时与多个方向发生关系。三条工作主线会并行推进，并通过代表性算例、环境和验收口径互相校验，不应被画成“工程预备完成后才开始性能专项，最后才进入架构设计”的线性流程。

这里列出的场景例子是解释对象关系的示例，不是经过项目确认的场景目录。

## 5. 任务、产出、证据与对外表达

一次项目实践通常会留下不同职责的记录：任务说明工作目标；产出保存工作结果；证据支持其中的事实或判断；评审确认产出的质量、归属和后续用途；对外作品再按受众组织获准使用的信息。它们相互关联，但不能互相替代。

```text
项目目标与范围
       │
       ├── 协作结构：谁参与、如何分工（具体内容以确认记录为准）
       ├── 工作主线：长期按什么方向组织工作
       └── 场景：本次实践处于什么条件
                    │
                    ▼
                  任务
                    │
                    ├── 形成任务初始产出
                    │        │
                    │        └── 经项目审查后，可晋级为主线长期资产
                    │
                    ├── 关联证据与来源，支撑限定条件下的主张
                    │
                    └── 选取已核验且获准披露的信息
                                   │
                                   ▼
                              对外表达作品
                                   │
                                   ▼
                          真人确认内容与发布授权
```

项目源仓库中的产出流程为：

```text
Issue 初始产出 → 项目审查与确认 → 对应工作主线的长期资产
                                       ↓
                           对外汇报按主题组织引用
```

这条流程表示文件职责和审查关系，不代表所有任务都必须晋级，也不代表晋级后的资产自动可以公开。对外作品应使用经过事实核验、符合披露边界的信息；是否发布仍需单独确认。

## 6. 必须分开的状态

判断项目材料时至少区分以下几类状态：

| 状态维度 | 回答的问题 | 不能据此推出什么 |
| --- | --- | --- |
| 项目阶段 | 项目整体目前处于什么阶段 | 不能证明某项技术结果已经验收 |
| 任务与产出生命周期 | 任务是否进行中、产出是否审查或晋级 | 文件已提交或已晋级，不代表公开授权 |
| 事实与证据状态 | 一个主张是已确认、有证据未验收、计划还是待核对 | 有报告、测试或会议记录，不一定构成正式结论 |
| 对外披露授权 | 某项内容、数据或作品能否面向特定受众使用 | 仓库为 public、材料已脱敏或工程检查通过，都不等于获得授权 |

具体状态应标注来源、日期、适用条件和确认责任。不同维度之间不自动传递结论。

## 7. 信息载体与事实主位

| 载体 | 主要职责 | 使用边界 |
| --- | --- | --- |
| Houzai 项目源仓库 | 项目上下文、任务导航、工作主线、研发和项目材料的主要入口 | 当前为 private；public 资产仓库只保留获准披露的摘要和必要来源标识，不复制受限正文 |
| 专业研发材料所在位置 | 保存源码、测试、实验记录和技术证据等专业内容 | 以原位置为事实主位；引用结论时保留版本、环境、口径和限制 |
| 本 public 资产仓库 | 保存脱敏项目上下文、表达任务、作品、来源关联和评审记录 | 项目材料进入仓库不等于已通过专业确认或获得发布授权 |
| `vendor/suanhai-team-external-expression-infrastructure/` | 固定版本复用团队通用表达工程能力 | 不承载大工项目事实；Manifest 未列出的能力不可当作已实现能力使用 |
| SuanhaiOS | 提供团队协作基础设施，可帮助成员进入项目任务并获取相应工作支持 | 它不是本项目技术事实、研发成果或对外授权的来源主位 |

若专业代码和项目资料共同维护在同一个仓库，应按目录与文件的实际职责判断主位，不要为了表格分类而假定一定存在独立仓库。

## 8. 对外表达任务如何使用项目上下文

制作项目概览、进展页或其他表达作品时，建议按以下顺序建立可追溯关系：

1. 在 `tasks/` 明确作品的受众、目的、范围、完成标准和责任信息；
2. 从本目录读取项目模型、概览、当前状态、工作主线和表达边界；
3. 为每项重要主张找到最接近的项目事实源，并标明事实状态、版本或日期；
4. 核实相应来源是否允许用于本次受众和用途，缺少授权时先保留为待确认；
5. 在 `works/` 形成作品，在 `reviews/` 记录事实核查、意见处理和真人确认；
6. 将专业正确性、表达质量、披露授权分别记录，不用其中一项替代另外两项。

本目录的摘要帮助发现应读什么，不能替代直接来源，也不能仅凭上下文摘要生成新的技术事实或承诺。
